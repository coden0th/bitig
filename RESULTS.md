# Results

Five measurement tools, deliberately measuring five different classes of error. A single
accuracy percentage would hide all of them.

| Tool | Question it answers | Needs labels? |
|---|---|---|
| `olc` | On cases we have labelled, are we right? Per-rule precision and recall. | yes |
| `altin_dogrula` | Is the gold set itself internally consistent? Never runs the engine. | n/a |
| `gidis_donus` | Can we re-parse everything we generate? | **no** |
| `kapsam` | How much of real Turkish do we see at all? Unparseable means a gap. | **no** |
| `soru_coz` / `fiil_coz` / `isim_coz` | Can we finish an actual past exam question? | external |
| `anlasmazlik` / `olay_hakemi` | Where do we disagree with an independent analyzer or a model? | **no** |

Run all of them with `python -m harness.<tool>`.

---

## Read this before reading the numbers

**The gold sets are partly self-authored.** Of 124 nominal-inflection entries, 17 currently
carry an explicit citation to official curriculum material (counted by grepping each record's
note field for a source citation); of 83 verbal-inflection entries, 4 do. The rest were
written during development and are being progressively replaced as sourced material becomes
available. A 100% score on labels you wrote yourself is not evidence of much, and it is listed
below with that caveat attached rather than quietly.

The measurements that do **not** depend on those labels are marked **[label-free]**. Those are
the ones to weigh.

## Against real exam questions

Questions from past national university entrance exams and official curriculum test banks.
Answer keys were never shown to the engine.

| Set | Result |
|---|---|
| Phonology | 12 correct, 2 ambiguous, **0 wrong** (of 14) |
| Verbs (voice, verbal nouns, compound tenses) | 8 / 8 |
| Noun compounds | 2 correct, 1 deliberately ambiguous (of 3) |
| Word formation | 7 / 29 mechanized |

The zero in the first row matters more than the twelve. When the engine cannot resolve a
question it reports ambiguity rather than committing to an answer. For a system whose output
becomes an answer key, a silent wrong answer is far worse than an abstention.

The 7/29 is reported unrounded because the other 22 are informative. They fail on a documented
structural boundary rather than on random error: words that the lexicon holds as bare roots
but the exam board treats as derived. Closing that gap needs a lexicalization inventory, which
is a data problem, not a code problem. Three theory sources were checked and none of them
closed it.

## Coverage **[label-free]**

| Corpus | Coverage |
|---|---|
| Clean generated Turkish text (400 sentences, 3,824 distinct words) | **97.83%** |
| Real exam text file (partly OCR-damaged) | 90.34% |

The first row is not exactly reproducible run to run: the text is freshly generated by a model
each time the tool runs, so sentence count and coverage shift slightly between runs (a prior
run measured 97.66% on 390 sentences). The number matters at the percent level, not the
per-mille level.

For reference, an independent frontier-model-assisted measurement on comparable text gave
96.86%. The gap between the two rows above is the OCR damage in the second file, not a
difference in capability; this was confirmed by measuring both.

Coverage scanning is how the two most serious engine bugs were found. Neither was caught by
any gold set, because the gold sets did not happen to include the affected stem shapes. One
of them (`-IcI`, among the most productive suffixes in Turkish) was broken for every
vowel-final stem: the engine produced `okucu` instead of `okuyucu`. The archetype had been
written with the wrong buffer-consonant syntax. This is the concrete argument for keeping a
label-free measurement in the suite.

## Round-trip integrity **[label-free]**

100.0000% over 226,583 generations, re-verified after every engine change. Whatever the engine
generates, it parses back.

This is the widest net available because it needs no labels at all. It also has a known blind
spot, worth stating: it generates from each lexicon root independently, so it cannot see a
constraint bug in the *middle* of a multi-step derivation chain. The aorist bug described in
ARCHITECTURE.md survived round-trip scanning for exactly this reason.

## Against an independent analyzer **[label-free]**

Compared against `zeyrek` on 207 words: 2 disagreements (`güdüğü`, `ufacığa`), and on review
the engine was correct in both. The word count grows as the lexicon and gold sets grow; an
earlier run at 181 words also found 2 disagreements, on different words.

## Derived engines

| Engine | Result | Network |
|---|---|---|
| Orthography, morphological errors | 100 / 100 generated cases | no |
| Orthography, lexical validity | 1,705 words cached, 97.8% valid | cache offline, sync online |
| Punctuation | 3 / 3 | no |
| Expression errors, word-list rules | 6 / 6 | no |
| Closed-class word classifier | 19 / 19 hand-built sentences | no |
| Context-sensitive reading selector | 5 / 6 | yes |
| Syllabification and vowel harmony | 44 unit tests, **not yet measured against real questions** | no |

The last row is listed as unmeasured on purpose. The rules match the official curriculum
definition and the language authority's published guidance, and they are covered by unit
tests, but no verifiable question source exists yet because this topic is very rarely tested.
Unmeasured is not the same as working.

The orthography test cases were not hand-written. Each correct word in the gold sets was
programmatically corrupted by inverting the engine's own evidence record (position, before,
after), producing 121 cases. Of those, 21 turned out to be independently valid words and were
excluded rather than counted, since the engine correctly parses them instead of flagging an
error.

## Model experiments

These are exploratory measurements, not production decisions. Nothing from them was fed back
into the engine, the gold sets, or the answer keys.

### Does a frontier model need the engine?

A frontier model was given the engine and curriculum text as tools, and tested on a
four-cell design: published past questions (which may be in its training data) versus original
questions written for the test and verified by the engine, each with and without tool access.

| | Published | Original |
|---|---|---|
| With tools | 76-82% | 87.5% |
| Without tools | 85% | 75% |

All four cells land in the same band. Neither memorization nor tool access made a decisive
difference, most likely because this model already knows standard Turkish phonology well.
**This does not generalize to a small model**, which is the actual deployment target, and that
comparison has not been run.

One recurring failure was observed across three separate cases: the model asserted a
phonological event that the tool had explicitly reported as absent. Tool access does not, by
itself, prevent hallucination about tool output.

### Small open-weight models

Tested on rented GPU hardware against 22 real word-formation questions, temperature 0.

| Model | Result |
|---|---|
| Gemma3-12B-it (vLLM) | 3 / 8 |
| Qwen3:8B (Ollama) | 2 / 8 |
| Qwen3.6:27B, default settings | 5 / 8 |
| Qwen3.6:27B, tuned, full set | 12 correct, 6 wrong, 4 format failures (of 22) |

Only the last row is a statistically meaningful comparison; the 8-question subsets are too
small for the differences between them to mean anything.

The "format failure" class was initially misdiagnosed as a generation loop. Minimal
reproduction showed the real cause: the reasoning trace and the answer share one token budget,
and on hard questions the trace alone consumed it, so no answer was ever emitted. Raising the
budget fixed most cases. Four questions resisted every combination tried, including disabling
reasoning entirely and doubling the budget again, which makes them a real capability limit
rather than a configuration problem.

A separate test asked whether a model can cover the engine's known lexicalization gap. On 12
words documented as failing cases, 9 historically derived and 3 genuine simple roots, the
model scored 11/12. That is real generalization rather than recall of one famous example, but
89% is below this project's threshold, and the single miss was on the most critical word. The
conclusion is the one the design already assumed: a model is usable as a candidate generator
and distillation source, never as an answer key.

## Known limits

Stated here rather than discovered later.

- **Lexicalized derivation.** Words the lexicon holds as bare roots but the exam board treats
  as derived. This blocks most of the word-formation domain and one phonological sub-pattern
  (compound verbs formed with auxiliaries). Needs a lexicalization inventory, and the
  inventory has to be finer-grained than first assumed: structurally identical word pairs
  behave differently.
- **Syntax.** Sentence constituents, transitivity, and valency are out of scope. Questions
  targeting them are not attempted.
- **Second-person singular imperative** is unmarked (zero affix) and therefore not labelled.
  Adding a synthetic marker was rejected as unmeasurable.
- **Multi-word compound verbs** are not modelled; the engine analyzes single words.
- **Questions targeting one underlined word** in a passage are skipped: the scanner reads the
  whole sentence, so another word carrying the same feature produces a false ambiguity.
- **Lexicon gaps** exist and are not patched silently. Where a root is genuinely missing from
  the upstream source, it is added through the override file and noted, not by editing the
  upstream copy.
- **Case-distinguishing diacritics** are partly unsupported, because dropping them blindly
  would merge genuinely distinct words. Determining where it is safe is a separate careful
  task and has not been done.
